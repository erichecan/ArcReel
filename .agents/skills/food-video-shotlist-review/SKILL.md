# 美食短视频分镜脚本审查

审查对象是喂给 AI 视频生成模型的分镜脚本,由若干"视频单元"(unit)组成,每个 unit 通常是几秒钟的一个镜头 + 一句台词。目标不是让描述更华丽,而是让每个 unit **值得单独存在**,并且写法本身更容易被视频生成模型正确渲染。

## 为什么这么审查(先讲透原理,再讲清单)

**多写字不会多花钱,但塞多个动作会让生成更容易失败。** 主流视频生成供应商基本都按"时长 × 分辨率 × 服务档位"计费,和 prompt 字数无关。真正的代价是间接的:一个 3~4 秒的 unit 里塞进两三个不同动作,当前的视频生成模型大概率处理不过来——要么动作糊在一起变形,要么只做出其中一个、其余被忽略。效果不满意,用户就要手动点"重新生成",这一次才会真的再计一次费。所以省钱的关键不是少写字,而是让每个 unit 只锁定一个动作,减少要重跑的次数。

**运镜是手段,不是内容。** 一个 unit 之所以让人觉得"就是个运镜,不值得",根源通常是画面主体在这几秒内**没有发生任何物理变化**——镜头在动,但没有东西被切开、翻炒、夹起、滴落。运镜的作用是引导视线去看一个变化,不能替代变化本身。

**Prompt 里词的顺序会影响生成质量。** 已验证的外部资料(2026 Director's Cheatsheet,覆盖 Sora 2 / Veo 3.1 / Kling 3 / Runway Gen-4)显示,这些模型对 prompt 中越靠前的词赋权越高,最佳固定顺序是:

```
主体(Subject) → 动作(Action) → 运镜(Camera movement) → 景别/焦段(Lens/framing) → 风格/光线(Style/lighting)
```

顺序打乱(比如把运镜或风格词放最前面)会明显降低生成质量。这意味着写 unit 描述时,先说"谁在做什么动作",运镜和景别放后面修饰,不要开头就是"镜头切向/镜头扫描"。

## 四问检查法(逐个 unit 过一遍)

对脚本里的**每一个** unit 依次问:

1. **画面主体在这几秒内发生了什么变化?** 如果答案是"没有变化,只是镜头在动",这个 unit 是弱的。
2. **这个变化能不能用一个动词说清楚?** 一个动词配一个 unit,不要在同一个 unit 里塞两个动词(比如"翻炒+装盘+冒烟"挤在一起,模型大概率只做出其中一个)。
3. **这个动作是否需要当前的景别/运镜来配合?** 比如"戳破酥皮"必须是特写+缓推才有意义,特写+固定就浪费了这个动作的看点。(参考下方"景别功能对照表"判断依据)
4. **去掉这个 unit,整条脚本是否会缺一个关键卖点或情绪节拍?** 如果去掉不影响,说明它本该被合并或删除。

任何一个 unit 只要在问题 1 上给出"没有变化"的答案,就判定为**弱单元**,需要改写或合并;其余三问用来判断改写方向和是否该保留独立存在。

## 景别功能对照表

四问法第 3 条("动作是否需要当前景别/运镜配合")容易靠临场感觉判断,漏检不容易发现。用这张表把判断依据固定下来——每种景别有它该承担的内容,用错了就是明显的弱点(比如全景拍不清"大口吃菜"的细节,特写脸部会让"竖大拇指"这种需要手部入镜的动作直接出画):

| 景别 | 该表现什么 | 不适合表现什么 |
|---|---|---|
| 远景/全景 | 环境、空间关系、场景转换(比如镜头扫过餐厅定格招牌) | 需要看清的手部/面部细节动作(咀嚼、拿筷子、竖大拇指) |
| 中景/中近景 | 人物完整的肢体动作、人与食物/器物的互动(翻炒、递菜、鼓掌) | 需要放大呈现的质感变化(拉丝、酱汁包裹、断面) |
| 近景/特写 | 手部动作、面部表情、食材/成品的质感细节(咬开断面、酱汁裹满) | 需要多个身体部位同框配合的动作(既要点头又要抬手) |
| 微距/大特写 | 极致质感瞬间(花椒滚动、油花爆开、拉丝断裂) | 需要交代动作起止过程的内容,信息量太满时观众会看不清主体是什么 |

判断方法:先确定这个 unit 的核心动作需要观众看清哪个部位/范围,再倒推该用哪个景别,而不是先定景别再往里塞动作。

## 镜头节奏结构

好的美食短视频脚本节奏大致是:

`工序特写(静态展示,建议全片不超过 1~2 个)→ 动作特写(有物理变化,应占多数)→ 全景/人物反应(情绪,1~2 个)→ 成品/CTA(1 个)`

审查时数一下静态展示型 unit(纯运镜、无主体变化)的占比——如果一条 8~9 个 unit 的脚本里有 3 个以上是纯静态/纯运镜,说明动作密度不够,节奏会显得拖沓、单薄。

## 整条脚本的检查(逐单元审查之外)

逐个 unit 过完四问之后,再回头把整条脚本当一个整体检查一遍,这些问题在单个 unit 里看不出来:

1. **时长是否对得上**:把所有 unit 的秒数加起来,和用户宣称的总时长比对。对不上(尤其差 5 秒以上)通常意味着漏了一个 unit,要点出具体缺口有多少秒,并检查 unit 编号是否连续(比如 `E1U7` 后面直接跳到 `E1U9`,中间的 `E1U8` 不存在)——编号跳号本身就是证据,不要假设是命名习惯,要向用户确认是否漏传。
2. **工序时间线是否合理**:这一条跟编号是否连续是两回事——编号可能完全连续,但内容顺序颠倒了。按 unit 编号当作播放顺序把工序过一遍(备料→烹饪→装盘/出锅→食用/反应→CTA),检查有没有"结果排在原因前面"的情况,比如成品已经装盘、食客已经在吃的镜头排在了炒制/倒料镜头之前。发现顺序颠倒要点名具体是哪几个 unit 编号冲突,并给出按工序应有的正确顺序。
3. **行为号召(CTA)前后是否统一**:扫一遍全片台词,看是否同时暗示了两种不同的转化路径(比如中段台词说"点外卖",结尾 CTA 又说"到店报暗号")。两种路径同时存在会让用户不清楚该做什么,转化效果会被稀释,必须收敛成一种。
4. **从社交媒体平台角度给整体评价**:除了逐单元的生成可行性,还要评价这条脚本作为一条投放内容的表现——开局 3 秒是否有能留住人的视觉/声音钩子、8~9 个 unit 拼起来是否构成完整的"种草→信任背书→行动号召"漏斗、CTA 是否明确可执行。这一层评价独立于四问法,是说给"这条视频能不能在平台上跑起来看"的,不要跟单元强弱判定混在一起。
5. **视觉重复度/留存曲线检查**:统计各 unit 的核心画面主体+场景组合(比如"厨师+炒锅"算一类),如果同一类组合在全片里出现 3 次以上,即使每个 unit 单独看都通过了四问法,拼起来也会让观众在中段(3~15 秒留存关键窗口)觉得"看过了",完播率下滑。发现这种情况要点名指出重复的 unit 编号,并建议把其中至少一个换成不同的视觉类型(比如从"炒锅动作"换成"人物反应"或"成品特写")。
6. **静音可读性检查**:短视频平台大量用户是默认静音刷视频的,台词/文案必须脱离声音、只靠画面+字幕也能被理解,不能设计需要"听清"才成立的信息(比如依赖语气词、拟声词才能传达的梗)。逐句过一遍台词,标出哪些信息点是纯听觉才能获取的,提示需要靠画面动作或字幕强调来补足。

## 美食动作动词库(参考,不必穷尽)

| 分类 | 动词 | 典型景别 + 运镜 |
|---|---|---|
| 备料 | 切、剁、揉、擀、腌、裹 | 近景/特写 + 固定或缓推,强调手部动作和食材质感 |
| 烹饪 | 下锅、翻炒、颠勺、勾芡、爆炒、炖煮 | 中近景 + 固定或轻微跟随,留出火光/蒸汽空间 |
| 成品 | 出锅、装盘、撒葱花、淋油、拉丝、冒烟、滴落 | 特写/微距 + 缓推或固定,突出质感变化的瞬间 |
| 食用 | 夹起、咬下、断面特写 | 特写 + 固定或轻微跟随,强调咀嚼/断面的瞬间细节 |

## 输出格式

目标产品(ArcReel)里每个 unit 的正文是独立的一个字段(不含 `[unit_id] (Ns)` 这层编号/时长前缀,那是另外两个字段拼出来给人看的),而且目前只能逐个 unit 手动粘贴回填、没有一次性批量导入的入口。所以每个建议修改的 unit 都必须单独给一段"可粘贴文本",内容严格等于改写后要填进那个 unit 正文字段的完整字符串(镜头描述 + `{台词}`),用户复制后不需要再手动删减任何字符就能直接贴进对应输入框——绝不能把 `[unit_id] (Ns)` 也算进这段文本里。

审查完一条脚本后,每个 unit 按下面的结构输出,不要只给结论不给理由:

> **[unit_id] 判定:强 / 弱**
> 理由:(对应四问里哪一条不通过)
> 改写建议:(如果是弱单元,给出包含"主体+动作+运镜+景别"顺序的具体改写方向说明)
> 可粘贴文本:
> ```
> (改写后的完整正文字符串,即镜头描述+{台词},不含编号和时长前缀)
> ```

判定为"强"、不需要改写的 unit 可以不给"可粘贴文本"这一块。判定为"应合并到其他 unit"的,把"可粘贴文本"放在合并后的目标 unit 条目下,并在被合并 unit 自己的条目里注明"内容已并入 [目标 unit_id],此 unit 可删除",不要重复给两份。

全部 unit 过完后,总结:静态展示型 unit 占比是否超标、整条脚本的节奏是否符合"工序→动作→反应→CTA"的分布、时长和编号是否有缺口、工序时间线顺序是否有颠倒、CTA 是否统一、是否存在视觉重复度过高的 unit 组合、台词是否具备静音可读性、最值得优先改的 2~3 个 unit。用户明确问"从平台角度怎么评价"时,把上面"整条脚本的检查"第 3 条的平台层面评价放在总结最前面。

不要在改写建议里堆更多动作——每次改写只解决"这个 unit 有没有一个具体动作"的问题,不要顺手加第二个动作进去。
